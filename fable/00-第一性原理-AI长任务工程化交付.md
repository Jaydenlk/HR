# AI 长任务工程化交付 · 第一性原理手册(可移植版)

> 目的:让任何模型(尤其 Opus 级)在任何项目里,不靠"聪明"也能稳定交付多天、多任务、多代理的长周期开发,质量达到"零带病合并"。
> 出处:2026-07 HRBP/Coach 二次重构实战蒸馏(6 任务全链交付、7+ 只真 bug 全部在合并前拦截、执行层全程 Sonnet)。
> 用法:新项目开工前读完本文件 → 按 §六 的移植清单落地 → 配套样例(本目录内)照抄改名。

---

## 一、五条公理(问题的本质)

一切机制都从这五条推出来。别背机制,理解公理——遇到没预案的新局面时,回到公理现推。

**公理 1:会话是易失的。**
配额耗尽、进程重启、上下文压缩随时发生,且不打招呼。任何只存在于"模型脑子里/当前会话里"的进展,都应视为已经丢失。

**公理 2:模型会走捷径。**
模型以最省力的方式满足字面要求:说"通过"不贴输出、跑了半套测试宣称全量、写占位测试凑覆盖、把"环境起不来"标成 SKIP 混过门。**报告不是事实,只有可复跑的证据是事实。**

**公理 3:判断力随任务长度衰减,且模型不自知。**
同一个模型,第 10 分钟的决策质量和第 3 小时的不是一回事;降档模型(执行层)在"分解任务、写派工要求、裁决边界情况"上最容易出错。它不会告诉你"我现在不太行了"。

**公理 4:错误不可根除,只能让它变便宜。**
再强的模型+再全的规则也会出错(包括协调者本人)。体系的目标不是零错误,是**每个错误在变贵之前被抓住**。

**公理 5:环境是脏的。**
端口被占、数据库迁移滞后、缓存残留、依赖沙箱、CRLF、worktree 特有故障、甚至终端输出被污染……环境失败会伪装成代码失败,或制造虚假的"成功"。分诊错了,就会"修"一个不存在的 bug,或放过一个真的,或相信一个没发生的提交。

## 二、由公理推出的八条铁律

| # | 铁律 | 推自 | 一句话操作定义 |
|---|------|------|----------------|
| 1 | **证据定义完成** | 公理2 | "完成"必须附可复跑证据(测试计数行原文/截图/命令输出)。`tsc --noEmit` 不是测试,编译过不是测试过。 |
| 2 | **增量提交** | 公理1 | 每完成一个清单条目立即 commit(`wip(<key>): <条目>` 即可)。中断时,已提交的就是断点,没提交的就是白干。※实战教训:同一任务曾三个配额窗口各烧 300k+ token、零提交、三次全损。 |
| 3 | **续跑判定** | 公理1 | 任何执行者开工先查"是否已有半成品"(git log 找本任务提交),有 → 缺口分析只做剩余,**不许重做、不许 revert 重来**。 |
| 4 | **判断前置** | 公理3 | 需要判断力的工作(任务分解、红线划定、判据制定、坑位标注)在设计期由最强模型写死成文档/脚本;执行期只剩"照做+如实报告"。执行者遇到文档没覆盖的决策点 → STOP,不许自作主张。 |
| 5 | **任务切片上限** | 公理1+3 | 单个执行代理的任务量以"一个配额窗口能收口"为上限(经验值 ≤10 文件或 ≤150k token 预估);更大的在派工层拆成串行段。同一任务被中断 3 次 = 结构性过大,禁止第 4 次原样重跑,改走"缺口审计→只补剩余"。 |
| 6 | **多闸互不信任** | 公理2+4 | 质量闸至少四道,每道抓不同类错误、互相不采信对方结论(见 §四)。实现者的自验不能替代独立审计;审计的 PASS 不能替代合并冒烟。 |
| 7 | **修复≤2轮 + STOP** | 公理3+4 | 同一任务修复最多 2 轮,仍不过 → 停下,把卡点/已试/建议写进账本等人。无脑重试是最贵的失败模式。 |
| 8 | **状态必核验,不信自述** | 公理2+5 | 任何"成功"输出(提交成功/推送成功/测试通过/代理已启动)都必须用**独立的干净读取**复核(git log/git cat-file/ls/重跑),尤其在环境可疑时。终端输出会被污染制造假成功;文件系统读取(Read/ls)比终端渲染可靠。 |

## 三、体系四件套(落地形态)

### 1. 文档层(唯一真相源,git 里,不在任何人脑子里)

```
00-总纲.md        状态追踪表(任务×[设计/实现/测试/审计/合并/部署]逐格打勾)
                  + 全局红线 + 执行进展账本(每任务一段:交付了什么/质量链/遗留)
                  + 待用户拍板项清单
01-开发纪律.md    环境坑位清单(哪条命令假绿/哪个目录跑不了测试/端口惯例/终端污染)
                  + 危险代码区(出过事故的模块:改动必跑哪些 spec、不变量是什么)
                  + 提交/部署纪律
02-执行手册.md    开工预检清单 + 任务→脚本索引表 + 通过判据(唯一标准,写死)
                  + 合并规程 + 修复循环规程 + 配额中断处置 + STOP 规则
```
每完成一步**立即更新 00 并核验**——这是断点续跑的生命线,也是对抗公理 1 的核心。

### 2. 脚本层(turnkey 派工脚本:把派工 prompt 预制成品)

每个任务一份脚本,三段式,要素缺一不可:

- **侦察段(只读)**:读设计文档 → 核对实时代码(行号会漂移,给"可 grep 的内容锚点"不给裸行号)→ 产出精确执行清单;文档点名但代码里找不到的标 `[缺失-需人工]`,**不许猜着补**。侦察先行的本质:吸收"设计文档写完后代码又变了"的漂移。
- **实现段**:操作规程(分支判定+工作区守卫+增量提交铁律)+ 设计定稿原文 + **红线清单**(明确"不做什么"和"哪些同名东西不许碰",比"做什么"更重要)+ 自验清单(每条命令写死,含已知假绿陷阱的规避写法)。
- **验证段**:测试门(逐门跑、每门附原始输出、失败贴全文)+ 独立审计(只读找茬,按编号列找茬重点,最致命的一条判错即 blocking)。

### 3. 角色层(权责隔离)

- **协调者(leader,最强模型)**:只做分解/派工/判定/合并/记账,**不写产品代码**。合并前必做 `git branch --show-current`(实战教训:执行者会把工作区留在 feat 分支,直接 merge 会"自己并自己")。
- **开发代理(执行层,普通档模型即可)**:一个任务一个代理,吃下侦察+实现+自验全程(上下文连续是质量来源);修复轮**继续用同一个代理**(SendMessage/续话),它有全上下文,最省 token。
- **审计代理(独立,只读)**:跨任务复用同一个(续话省新开);立场是"找茬不背书";它与开发代理永不互通,只经协调者转述。
- 省配额要点:新开一个模型实例的成本远高于续用(上下文缓存),能续用就续用;每任务净新开数压到 1。

### 4. 调度层(双保险,对抗公理 1)

- **心跳 cron(每 30 分钟)**:唤醒 prompt 写死"状态检查→有活干活/没活报平安→坐标(记忆文件+00+02)→铁律"。注意会话级 cron 随进程重启消失——记忆文件里写死"发现 cron 没了立即原样重建"。
- **记忆断点文件**:每个关键节点后更新,格式固定:当前 in-flight 是什么(代理 ID/分支/进度)+ **"若本实例中断,下一步动作是什么"逐步写死**。让任何冷启动的续跑实例 5 分钟内接上。

## 四、质量闸(每道抓不同的错,顺序固定)

| 闸 | 执行者 | 抓什么 | 判据要点 |
|----|--------|--------|----------|
| 1 自验 | 开发代理 | 低级错误 | 全量单测+全量 e2e+lint+build,**每条命令写死**(含假绿陷阱:如 jest 默认 testRegex 匹配不到 e2e 文件,必须单独 `--config` 跑,否则"全部通过"是假的) |
| 2 独立审计 | 审计代理 | 实质缺陷/越界/敷衍 | blocking 清零才放行;major 记遗留不阻断(同类累计≥3 升级);minor 只记录。**协调者应给审计加"本任务特有的致命核点"**(如"迁移清洗必须 SET NULL 不许 DELETE 行") |
| 3 实机走查 | 开发代理或测试代理 | 静态检查测不出的运行时行为 | 涉前端/用户可见行为必做(Playwright 真点按钮);"环境起不来"≠过,按铁律 8 分诊。※实战:唯一一只 blocking 级产品缺陷(并发双扣费竞态)就是这道闸抓的,前两道全没发现 |
| 4 合并三验 | 协调者 | 合并环节本身 | ①树一致性:合并后 `git diff <feat分支> <主干> --stat` 必须为空(=合并零引入);②主干冒烟(全量测试+build 重跑);③基线对账(测试计数=分支交付计数,差额必须能解释)。**每一验的结果都要干净复核,不信一次性输出** |

**裁决纪律**:判据是唯一标准,不许凭感觉放宽;但也不许拿 minor 压成 FAIL 制造无谓修复循环。审计报回 major 时,协调者要问一句:"这条 major 是不是本任务本来要根治的核心场景?"是 → 修完再合并,别拿"手册说 major 不阻断"当挡箭牌。

## 五、异常处置决策树(症状→动作)

**配额中断(执行者死于 session limit)**
→ 立即查工作区:有未提交改动 → 协调者代为 `git add <本任务路径> && git commit -m "wip: 抢救性提交"`(危险区改动先打 diff 快照到仓库外);→ 断点写进 00+记忆 → 恢复后走"缺口审计(只读+探针,DONE/PARTIAL/MISSING 逐项判)→ 只补缺口(增量提交)→ 正常验证",**永不从头重跑**。

**同一任务三连死**
→ 结构性过大,按铁律 5 拆;已有半成品的走上面的缺口流程。

**环境未就绪(端口占用/迁移滞后/依赖缺失)**
→ 铁律 8 分诊;残留服务进程跑的是旧代码,测试前必须停掉重起本分支的,否则测的是别人。

**终端输出污染(假成功/幻觉数字/自相矛盾)**
→ 立即改用文件系统读取(Read/ls/写文件再 Read)核验真实状态;git 操作后一律 `git log`/`git cat-file -t <sha>` 复核提交是否真的存在;不信任何未经独立复核的"成功"。※实战:一个会话曾幻觉出根本不存在的提交、推送、代理启动,靠 `git cat-file` 发现 sha "Not a valid object name" 才揭穿。

**测试挂了:脆弱测试还是真回归?**
→ 在基线(主干)上跑同一条:基线也挂 = 既有问题,单独立项修(别混进当前任务);基线绿 = 你的回归,修你的改动而不是改测试。改测试让它变绿是最后手段且要独立说明理由。

**进程重启(后台任务全灭+会话 cron 消失)**
→ 后台代理的产出如果没落盘就没了,但增量提交保住了 git 里的一切;重建 cron;有 runId 的工作流用 resume 续(完成段走缓存)。

**git 缠绕**
→ 树操作只允许协调者单线程做,永不派代理"帮忙清理";合并前 `git branch --show-current`;占用中的工作树对协调者 git 只读。

## 六、移植到新项目的步骤清单(step→verify)

1. 建 `docs/<战役名>/` 三件套(00/01/02),01 的环境坑位先空着,踩一个记一个 → verify:三文件入库。
2. 用最强模型做一轮**设计定稿**(和用户逐项确认)+ 一轮**代码现状审计**(实锤到 file:line),审计结论校准进各任务文档 → verify:用户对每个任务说过"可以"。
3. 每任务写 turnkey 脚本(§三.2 三段式;红线与假绿陷阱是灵魂)→ verify:另一个模型冷读脚本能复述出"做什么/不做什么/怎么算过"。
4. 定质量闸判据(§四表格抄走改数字)写进 02 → verify:判据里没有任何"视情况""酌情"。
5. 建心跳 cron + 记忆断点文件(模板见 §三.4)→ verify:手动杀会话再冷启动,新实例能在 5 分钟内说出下一步。
6. 首任务先跑最小的一个,全流程走一遍(开发→审计→合并三验→入账),把过程中踩的坑回填 01/02 → verify:第二个任务开始不再踩同类坑。
7. 从此循环:预检→派工→判定→合并→入账→下一个;出 bug 就地修(≤2 轮),没 bug 持续推进。

## 七、为什么信这套(实战数据)

HRBP 二次重构(2026-07-02 至 07-04,线上有真实用户):
- 6 个任务全链交付合并(危险区并发修复/导航重构/搜索服务重设计/详情页/情报流水线/schema 焊死),主干**零带病合并**。
- **7+ 只真 bug 全部在合并前被体系拦截**,分布证明"多闸互不信任"必要:实现者自验抓到 2(同批 upsert 竞态、迁移列型不符),独立审计抓到 3(缓存拒绝无重搜、跨请求竞态、双端约束不对称),实机走查抓到 1(并发双扣费,前两道闸全漏),真机迁移抓到 1(varchar→uuid)。
- 执行层全程 Sonnet;协调者的价值集中在判定尺度与派工核点,不在写代码。
- 反面教材同样有数:增量提交铁律出台前,同一任务三个配额窗口共 1000k+ token 全损;出台后再无一次超过"一个条目"的损失。终端污染一夜制造多起幻觉提交,靠"状态必核验"铁律逐一揭穿,零误信落地。
