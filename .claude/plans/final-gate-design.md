# 上线前终验门设计(用户指令 2026-06-13)

## 触发条件
第二轮迭代 **3 批全部开发完成并合入 dev** 后执行(第1批点数同步/tooltip/行业趋势 + 第2批 career 可信度 + 第3批 Coach 宏观层)。**未到此条件不执行。**

## 用户原话要求
"用 fable 预设和另外发配一个 dynamic workflow 单独做一批上线前的审计和测试,然后做交叉验证,不准造假,允许高并发,可以用 opus4.8,token 很够随便并发,要效率 max 别省,但要保证质量,你敢保证没任何问题再上传服务器公测。"

## 设计:交叉验证 dynamic workflow(高并发 + Opus + fable-dev)

核心反造假机制 = **没有任何结论是单点自证的**。三层交叉:

### 第一层:多维度并行深度审计(fable-dev 预设,Opus,高并发)
按维度切面,每维度一个 fable-dev agent 独立深审(agentType: 'fable-dev', model opus)。维度(随最终代码态调整):
1. 防编造/可信度 — 能力盘点(career evidenceFound/证据铁律)、模拟面试公司层、行业趋势博查来源、Coach 标源,所有 AI 输出有无编造护栏 + 真跑构造编造场景看会不会编
2. 计费正确性 — credit 扣点/流水/事务行锁防双扣/余额两处同步/402/SSE 流完成才扣/中断不扣
3. 安全 — IDOR/越权/owner-only 404/密钥纪律/输入长度校验/prompt 注入面/handoff 信任边界
4. 数据安全 — 所有 migration 是否纯加法不伤存量/事务/回滚路径/存量用户补点对账
5. 资源稳定性 — SSE 断连释放并发槽/卸载取消/缓冲上限/2C2G 内存/博查超时降级
6. 前端运行时 — 全流程真点真走(Playwright)、空态/错误态、移动端拦截、tooltip、行动卡片全链
7. 回归 — 本轮没碰的老功能全量过一遍没被搞坏

### 第二层:实证交叉(test-agent E2E 真跑)
独立于审计,test-agent 起真服务 + Docker Postgres 真跑。规则:**审计说"有问题"必须 E2E 能复现;E2E 说"过了"审计的逻辑判断要一致**。两边结论比对,矛盾处进第三层。

### 第三层:完整性批评家(反造假专岗)
一个独立 agent 专审前两层的所有产出,只干一件事——抓水分:
- 哪条 PASS 没附原始证据(测试输出/截图/curl)?
- 哪项被悄悄跳过没声明?
- 哪个"已验证"其实是静态看代码没真跑?
- 哪个维度漏了没覆盖?
发现即打回重验。它找到的就是下一轮要补的。

### 收敛规则(loop-until-clean)
任一层报 P0/P1 → 修复批 → 重跑相关维度,直到**连续一轮无新发现**才算过。不设固定轮数。

## 我(协调者)的签字流程
全部维度绿 + 完整性批评家无造假发现 + **我亲自抽查每个维度至少一条原始证据**(不信报告信证据)→ 才出"可以公测"判决书,列明:已验维度清单 + 每维度关键证据 + 残余风险(诚实列,不藏)。

## 担保边界(诚实校准,不造假)
不担保"绝对零 bug"(造假)。担保:① 已知维度交叉验证全绿且有证据;② 反造假岗兜底;③ 残余风险透明。即"没有我知道却瞒着你的问题"。

## 部署铁律(终验过后)
先 GitHub(已 tag prod-b24521d 兜底)→ 本机彩排(含 auto-v2 中转流式补冒烟)→ 服务器 pg_dump 备份(确认落地才迁移)→ migration(纯加法)→ up -d → 公网真浏览器实测 → 才算上线公测。生产 DEV_LOGIN=0 无例外。
