# 防降智保险方法论(可移植版)

> 适用场景:项目由 AI 模型(或水平波动的执行者)长周期执行,强模型窗口有限,执行期可能被降级到弱模型。目标:**执行模型降智,产出质量不降级。**
> 本文来自一个已上线 SaaS 项目的实战蒸馏:每条规则背后都有一次真实翻车,反面案例全部保留——规则没有事故背书就只是口号。
> 你们正在写 PRD,这是最佳时机:防降智的 80% 工作量在设计期,PRD 阶段埋下的每个判据,执行期都省十倍纠错成本。

---

## 一、核心思想:智力前置

降智本身不可怕。可怕的是把**需要判断力的环节**留给降智后的模型:

- 任务怎么拆?(分解)
- 派工 prompt 怎么写?(转译)
- "做完了"怎么算?(验收解释权)
- 遇到没料到的情况怎么办?(现场决策)

这四件事弱模型全都做不好,而且**错得悄无声息**——它不会说"我不行",它会自信地给你一个走样的执行。我们吃过的最大亏:一个降级模型自主开发流式看门狗,方向、参数、验证全走样,酿成生产事故。

**对策只有一条:强模型在位时,把所有判断力密集的工作做完、固化成文字;弱模型的动作被压缩到机械三步——跑预制任务 → 按写死的判据读结果 → 合并或停下问人。**

类比:民航不靠"每个机长都是天才"保安全,靠的是 checklist 把天才的判断固化成人人可执行的程序。你们要给项目写的,就是这套 checklist 体系。

## 二、七大机制(每条:做法 + 踩过的坑 + 落地要点)

### 机制 1:文档分层,唯一入口,执行期零架构决策

**做法**:三层文档 + 每任务一份设计定稿。

| 层 | 内容 | 关键特征 |
|----|------|----------|
| 00 总纲 | 任务顺序/依赖/红线/**状态追踪表**/已拍板决策存档/待用户输入清单 | 唯一入口;任何模型接手先读它 |
| 01 行为纪律 | 证据标准/环境坑位表/危险代码区/熔断线/提交纪律 | **全部命令句,不解释哲学**——弱模型读哲学会自由发挥,读命令句只能照做 |
| 02 执行手册 | 三步动作/通过判据/STOP 规则/合并规程/修复循环/任务索引表 | 执行者的全部世界 |
| 每任务设计文档 | 设计定稿+现状坐标(file:line)+改动清单+红线+step→verify | 设计争论在这里终结,执行期不重开 |

**踩过的坑**:早期"计划写在对话里",模型一换、上下文一压缩,计划就变形。文档必须落盘、必须进 git、必须有唯一入口——不能指望执行者"记得"。

**落地要点**:
- 总纲开头写死导读链:"先读 00 → 01 → 02,然后照手册跑,**不要自己分解任务、不要自己写派工 prompt**"。
- 状态追踪表每完成一步立即更新——这是断点续跑的生命线(见机制 6)。
- 用户已拍板的决策**逐条存档**并标注"执行期不得重开讨论"——弱模型最爱干的事就是把定过的方案重新发明一遍。

### 机制 2:决策全部写死,授权边界明确

**做法**:把执行期可能遇到的每类情况预先分成三档:

1. **能自己定的**(写清楚):行号漂移按内容锚点继续、prompt 措辞微调、失败后组织修复。
2. **必须 STOP 问人的**(写清楚):扩大范围、跳过质量门、放宽判据、合并两个任务、任何不可逆操作(部署/删数据/删表)、文档没覆盖的决策点。
3. **待用户输入的遗留项**(单列清单):执行到对应节点才索要,不阻塞其他工作。

**踩过的坑**:没写授权边界时,弱模型的两种死法:要么自作主张越界(悄悄扩范围、顺手重构),要么畏手畏脚每步都问(等于没有自动化)。边界写死后两种死法同时消失。

**落地要点**:STOP 不是失败,是设计好的安全出口。明确规定 STOP 时的动作:在状态表写清"卡点/已试过什么/建议下一步",然后等人——**不许无脑重试**。

### 机制 3:任务预制成"侦察先行"的可执行单元

**做法**:强模型在位时,把每个任务做成一条可直接运行的编排脚本(或等价的详细执行卡),内部固定三段:

1. **侦察段(只读)**:运行时重新核对设计文档与实时代码,产出"当前精确执行清单"。**文档里的行号只是线索不是圣旨**——代码会漂移,清单锚点必须用"可 grep 的独特字符串"而非裸行号。文档点名但现实里找不到的条目,标 `[缺失-需人工]` 并 STOP,**绝不允许猜着补**。
2. **实现段**:拿着侦察清单逐条执行,每条给 DONE/SKIP+证据;自验(残留扫描+编译探针)后只提交本任务文件。
3. **验证段(并行)**:测试代理跑全部质量门 + 审计代理只读找茬,互不通气。

**踩过的坑**:预制脚本如果写死行号/现状,几天后代码一动就全错。"侦察先行"让脚本自己吸收漂移——这是预制任务能存活超过一周的唯一办法。

**落地要点**:
- **prompt 自足性**:执行子单元是无状态的,不会脑补。每个 prompt 必须自带全部文件路径、完整验证命令、红线全文。"见上文"三个字在派工 prompt 里就是事故。
- 每个任务的派工五件套:任务一句话 / 输入文件清单 / 禁止触碰清单 / 交付物与写入位置 / 验证命令。
- 红线要写"禁碰的同名陷阱":我们删一个薪资模块时,预先列出了五个"同名不同物"的字段(别的模块自己的 salary_range 等),实现者一个没误伤——不列的话必死。

### 机制 4:验收 = 机械判据,消灭解释权

**做法**:验收结果必须是结构化的、可布尔判定的,弱模型只做"对表",不做"理解"。

- 测试代理返回 `{gates:[{name,pass,evidence}], overall_pass}`;审计代理返回 `{verdict: PASS|FAIL, findings:[{severity,file,issue,evidence}]}`。
- 通过判据写成硬条件:`overall_pass===true` **且** 审计无 blocking **且** 残留扫描符合白名单,**缺一门不许合并**。
- 严重度裁决规则写死:blocking 必须清零;major 记遗留不阻断(同类累计≥3 升级必修);minor 只记录。
- **合并后加一道轻量对抗审计**:单个代理、对抗立场、只审合并 diff,专找冲突解错/半合并/红线触碰。"保证没问题即收工"——明令禁止为凑发现报鸡毛蒜皮(防审计通胀浪费 token)。

**踩过的坑(重要)**:**基线必须先绿**。我们有 4 条 e2e 因为"测试种子写死了 2026Q2、系统按当前季度过滤"而恒红。这种既有红灯不清掉,弱模型永远分不清"我改坏的"还是"本来就红",判据直接失真。**开工第一件事:把存量恒红测试修绿或显式隔离,然后规定"允许失败数=0",不留任何'已知失败白名单'让执行者自由心证。**

**落地要点(给 PRD 的)**:PRD 里每个功能的验收标准写成**可执行命令+期望输出**,不写"功能正常""体验流畅"。"添加校验"→"对这批非法输入写测试并使其通过";"修复 bug"→"先写复现测试再让它变绿"。写不出验证方式的需求 = 需求本身没想清楚。

### 机制 5:假绿灯防御(证据文化)

这是整套体系里最容易被低估、又最致命的一层。**弱模型不会撒谎,但它特别容易被工具骗,然后真诚地把假绿灯汇报成通过。**

**真实案例**:我们的 e2e 测试文件以 `-spec.ts` 结尾,而裸 jest 命令的 testRegex 只匹配 `.spec.ts`——裸 jest 会 **0 匹配、静默跳过全部 e2e、报"全部通过"**。也就是说:一个执行者可以"跑了测试、全绿、有输出",而最核心的验收用例一条都没执行。这个雷是我们对预制脚本做对抗校验时抓到的,当时脚本已经写好、看起来完美。

**做法**:
1. **"没有证据=没有完成"**:每个 verify 必须附原始命令输出(统计行原样贴),FAIL 不许粉饰成 minor。
2. **证据绑定命令**:声称"e2e 通过"的证据,必须来自那条**带特定 config 参数**的命令的输出;把每条命令陷阱(哪个目录跑、带什么参数、为什么)写进 01 纪律,并注明"别手贱改回去"。
3. **概念不许偷换**:编译通过≠lint 通过≠测试通过;截图存在≠功能可用(前端必须真实走用户流:点按钮、填表单、断言结果,我们甚至要求断言图片 naturalWidth>0 来证明"头像没裂",因为"元素存在"和"图片加载成功"是两回事)。
4. **修测试的任务专设"松绑检查"**:审计必须逐条对比断言强度——把 `>0` 改成 `>=0`、删用例、加 skip,任何一种=blocking。弱模型"修测试"的默认动作就是把测试修没了。

### 机制 6:状态外置 + 断点续跑(anti-中断)

**做法**:假设执行随时会被掐断(token 耗尽/进程死/换模型),任何时刻的进度都必须能从磁盘恢复:

1. **每任务收口四件套**:合并 + 推送 + 更新状态表 + 更新断点记录。做完一件落一件,永远不欠账。
2. **断点记录写精确坐标**:进行中任务的脚本路径、运行 ID、分支名、下一步动作——让续跑实例零考古接手。
3. **编排系统选支持"断点续跑"的**:已完成的子任务结果缓存,重启后跳过重放,只跑没完成的。
4. **定时唤醒兜底**:设周期性定时任务,唤醒 prompt 完全自足(读哪份断点、判据在哪、铁律是什么、"用户在睡觉不许提问");活着的实例发现无事可做就静默退出。
5. **配额失败≠质量失败**:因限流/网络挂掉的执行轮**不计入重试次数和质量结论**。我们吃过的亏:5 个任务被限流打成 null 却计入了轮次上限,全部被错误标记为"质量不达标"——差点把好东西当废品扔了。

### 机制 7:模型分级 + 反优绩主义(质量和成本同时守住)

**做法**:
1. **判断力分级用模型**:高危环节(碰过生产事故的代码、语义审查、对抗审计)用高档模型;机械环节(格式转换、照模板渲染)用低档模型;**确定性检查一律脚本化**——字段完整度、黑名单、残留扫描这类事,脚本比任何 LLM 更便宜也更可靠。
2. **危险代码区制度**:把出过事故的文件列成名单,规定"改动这些文件后,当次必须跑指定测试到全绿才许下一步",并写明不变量(例:"槽位只在 finally 释放")。这是给弱模型的护栏,也是给强模型的。
3. **行为熔断线**:同思路失败 3 次换思路;同问题缠斗 8 次停下写卡点;修复循环最多 2 轮;单个网络请求必须带超时放弃逻辑(我们有过一个挂死的网页抓取冻结整条流水线 40 分钟的事故)。
4. **反优绩主义(防流程自嗨)**:所有流程指标(审查轮数、源数量、门数)都不是目标本身。每道质量闸要在试点批**自证抓到过真问题**,抓不到真错的闸直接砍掉。验收北极星是"产出对真实用户有没有用",不是"流程分多高"。我们曾有一版流水线,7-8 轮审查结果反而更差——因为修复方式是整体重写,每轮改掉旧错的同时引入新错。**质量来自断言级的具体检查,不来自审查遍数。**

## 三、PRD 阶段现在就该做的(checklist)

你们在写 PRD,以下每条现在做,成本最低:

- [ ] **每个需求配可执行验收**:命令/操作步骤 + 期望输出。写不出来的需求打回重想。
- [ ] **划清决策归属**:哪些是产品拍板项(变更要走人)、哪些授权执行者自定(写清边界)。PRD 里就分好,执行期不扯皮。
- [ ] **红线与需求同级**:不许做什么(禁碰模块/不可逆操作/数据红线)和要做什么一样重要,写进同一份文档。
- [ ] **术语表+唯一事实源**:每个关键概念一个定义,防止执行期"每个任务重新协商一遍这个词什么意思"——重复协商就是 token 和质量的双重杀手。
- [ ] **状态追踪表从第一天建**:任务×阶段的格子,规定"做完立即打勾"。
- [ ] **先建质量门再写功能**:测试基线全绿、lint 零错、验收命令跑通,然后才开第一个功能。带病基线会污染之后所有判据。
- [ ] **预留 STOP 协议**:执行者卡住/越界/遇到未覆盖决策时的标准动作(写卡点→等人),写进 PRD 附录。
- [ ] **计划模型降级预案**:明确"如果执行模型被降级,哪些环节必须升档模型/加人工复核"——至少把危险模块清单列出来。

## 四、反模式速查(见到就纠)

| 反模式 | 症状 | 纠法 |
|--------|------|------|
| 智力后置 | "先开工,细节执行时再定" | 判断力工作全部前置到设计期 |
| 验收凭感觉 | "看起来没问题""基本可用" | 机械判据+原始输出证据 |
| 假绿灯 | 跑了命令有输出就算过 | 证据绑定到特定命令;核对统计行里的用例数 |
| 已知失败白名单 | "那几个红的是老问题,忽略" | 修绿或显式隔离,允许失败数归零 |
| 修测试=删测试 | 断言变弱、用例被 skip | 审计专设松绑检查,松绑=blocking |
| 审计通胀 | 为显得认真报一堆鸡毛蒜皮 | "保证没问题即收工",闸要自证抓到过真错 |
| 重新协商 | 每个任务重新讨论已定决策 | 拍板决策存档+“不得重开”标注 |
| 无脑重试 | 同一失败原样重试 N 次 | 熔断线:3 换路、8 停下、修复 2 轮封顶 |
| 配额当质量 | 限流失败计入质量结论 | 基础设施失败不计轮次,恢复后重跑 |
| 状态在脑子里 | "我记得做到哪了" | 状态表+断点文件,每步落盘 |
| 行号当圣旨 | 预制清单写死行号,漂移即崩 | 内容锚点+运行时侦察核对 |
| 流程自嗨 | 门越加越多,产出没变好 | 每道门自证价值,砍掉不抓真错的 |

---

## 五、一句话总结

**把"聪明"花在设计期,把"服从"留给执行期;让每一次"完成"都有机器可核验的证据,让每一次"没把握"都有写死的安全出口。**

做到这两句,执行模型降几档,产出下限不动。
