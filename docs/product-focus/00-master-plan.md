## 3. 三核心+支撑服务的边界定义

**付费核心**(资源倾斜,质量门最严):
1. 校招职业标尺诊断(按目标职业/校招阶段逐条指出哪里不成立、为什么、缺什么证据)
2. 证据绑定的逐条改写与版本交付(原文/改后/理由/依据/安全采纳/完整版本导出)
3. JD 定制投递版本(真实经历对 JD 调整强调与表达,零编造)

**支撑服务**(保留,服务于核心或用户体验完整性,不再独立扩张):
- 点数体系(计费载体,保持现状)
- 模拟面试、月刊校招情报、ASR 面试复盘(用户否决砍单,保持现状运营)
- 投递追踪(承接求职信并入+效果闭环数据的落点)
- 公司背景调查(藏于投递详情)
- AI 对话教练(上下文追问定位)
- T3 职业维基(诊断的 rubric/证据基础设施;独立前台=低优先级不上主导航)

**红线**:支撑服务只做维护级改动;新功能扩张必须先过"是否直接强化三核心"审查。

## 4. 效果闭环埋点规格(WP-2 摘要,运营后台向)

采集链(全部后台,无用户可见新 UI):
```
diagnosis_suggestion 事件:展开/复制/采纳/拒绝(拒绝原因枚举:不真实/表达不自然/没帮助/已经有)
→ resume_version:哪个版本源自哪些 suggestion
→ application:该投递用了哪个版本
→ application_stage:是否获笔试/面试/终面(用户在投递追踪中更新状态即为采集点)
```
产出:admin 后台聚合查询(按职业/按 rubric 维度的采纳率、版本→获面转化)。不宣称"提高 offer 率"直到有样本。隐私:不采集企业未授权信息;用户数据留本库不出境。

## 5. 协作协议(GPT ↔ Claude 交接,双向适用)

1. **唯一真相源**:本文档状态表 + 各 WP 技术文档 + git 提交历史。会话记忆/平台侧记忆一律视为暗示不作依据。
2. **接手仪式**:读本文档→`git status`+`git branch` 确认干净在 dev→读目标 WP 技术文档→按其 step→verify 执行→**每完成一步立即更新本文档状态表并 commit**(断点续跑生命线)。
3. **证据纪律**:完成=附可复跑证据(测试原始输出/命令结果);`tsc --noEmit` 不是 lint;裸 `npx jest` 不是 e2e(e2e=`npx jest --config ./test/jest-e2e.json --forceExit`)。
4. **验收门**(改代码必过):api 单测+e2e+build,web `npx eslint src` 0 错+build;涉前端加 Playwright 实测;统一入口 `node scripts/run-gates.mjs`。
5. **git 纪律**:worktree 开发;合并前 `git branch --show-current` 确认在 dev;推送=`git push origin dev && git push origin dev:main`;密钥永不入库;迁移一律手写。
6. **红线**:未裁决事项(本文档 §1 末段)遇到即停问用户;不顺手重构;每行改动可追溯到 WP;破坏性操作(删表/覆盖用户数据)先确认备份回滚。
7. **T3 专属**:执行细节以 docs/refactor2/ 体系为准(00-master-plan→T3-career-wiki→t3-codex56-review→t3-gate-a-taskcards);restricted 数据(考公/国企)永不上生产,遇到相关文件先读 t3-codex56-review §R4。
8. **文风**:向用户汇报用中文说人话,先结论后展开。
