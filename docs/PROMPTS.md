## A. 任务总控(每个任务贴一次,填空)

```
【需求】
{用业务语言讲清:谁、在什么场景下、要完成什么、做成了长什么样}
业务链路:{入口 → 每个环节 → 出口,逐环节写清。这是验收的唯一基准}
不在范围内:{明确不做的事}

【执行纪律】
1. 全程遵循 using-superpowers skill。以下 skill 按条件强制加载,任何一个找不到
   → 立即停止任务并报告,严禁在没有 skill 的情况下裸跑:
   - 涉及前端 UI:frontend-design + uiuxpromax
   - 开发完成后依次:Simplify(代码审查)→ PJR(前后端都要 lint+build,
     eslint 0 错才算 lint,tsc --noEmit 不算)→ Playwright 端到端验收(见验收标准 C/D)
     → git-merge-to-dev 合并回 dev(rebase 后合并)
2. 开发一律在 worktree 执行(确属琐碎任务可豁免,但要先声明并说明理由)。
3. 动手前先充分探索现有代码:列出"将复用 / 将改动 / 将删除"的文件清单,再写第一行代码。
4. 任务拆成 step→verify:每步 = 一个动作 + 一个可独立运行的检查命令 + 期望结果;
   做完一步立刻验一步,不许攒到最后。

【红线(违反任何一条 = 返工,没有商量)】
- 严禁打补丁:不许为绕过问题加特判、包一层、复制一份。必须找到根因,通过重构或
  融入现有逻辑实现,最终代码要像"本来就长这样"。"最简"指结果最简,不是过程省事。
- 严禁 mock 数据上前端、严禁空按钮、严禁 TODO/占位实现混过验收。
- 范围纪律:每行改动可追溯到本需求;不顺手重构无关代码、不加没人要的配置项。
- 完成的定义 = 每个 verify 都有 PASS 证据(命令原始输出/截图)。无证据按未完成处理。
- 同一问题卡 3 次换思路,卡 8 次停下来报告(卡在哪/试过什么/建议),严禁无脑循环。

【交付物】
1. 改动文件清单 + 每步 verify 的 PASS/FAIL 与证据
2. 测试报告(按前端/后端验收标准执行,含原始输出)
3. 遗留问题与风险清单(没有就写"无",但这等于你签字担保)
```

## B. 开发原则(常驻)

```
开发原则(强制,逐条可裁决):
1. 单一职责 —— 每个服务/方法只负责一个明确的职责域,职责混了就拆。
2. 最简代码 —— 不做向后兼容,宁可破坏性更新;冗余代码一律删除。
   "最简"以结果裁决:同样的需求,代码更少更直白的方案胜出。
3. 类型严格 —— 禁 any、禁 as unknown as、禁 @ts-ignore;类型/编译错误当场修,不留到以后。
4. KISS —— 需要解释才能看懂 = 太复杂,重写;200 行能写成 50 行就重写。
5. 文档置信度 —— 绝不基于推测写代码,必须基于真实可验证的技术文档;
   训练记忆与当前日期差距大的框架/API,先查官方文档再写。
   涉及支付/数据库/外部 API 等关键功能,文档置信度不足 → 停下来要准确资料,而不是猜。
6. 根因修复 —— 任何修改/修复/新增都不得以补丁形式存在,必须深度融合进代码逻辑
   (重构/调整/结合现有逻辑)。"清缓存重启就好了"不是修复,是掩盖。
7. 证据文化 —— 编译通过 ≠ lint 通过(eslint 0 错才算);代码写完 ≠ 测试通过(真跑才算);
   "已完成"三个字必须可复跑验证,否则视为虚报。
```

## C. 前端验收标准(常驻)

```
用 Playwright 直接驱动真实浏览器验收——不是写测试脚本留档,是当场把产品当用户用一遍。

覆盖要求:
- 桌面 + 移动两种视口都要测(产品明确不支持移动端时,改测移动拦截提示是否生效)。
- 把需求的完整业务链路代入具体场景执行:每个按钮点到、每个输入框填到、每个跳转走到。
  看到页面渲染 ≠ 验收;必须完整交互,从入口一路走到链路终点。检查的不只是 UI,还有 UX。
- 场景两类,缺一不可:
  ① 正常剧本:一个真实用户带着真实目标,从入口完整走到出口,中途数据要像真的。
  ② 边界剧本:空输入 / 超长输入 / 非法格式 / 重复提交 / 越权访问 / 中途刷新 / 接口失败,
    验证异常被预期内拦截,且错误提示说人话、符合当前场景。

心态与口径:
- 找茬,不是确认:我们不是要验证它对,而是要验证它有错,一定要找出错来。
- 不只看布局:文案内容是否符合当前场景、数字是否真实来自 API(严禁页面上有编造数据)、
  空状态/加载态/错误态是否都处理了、交互反馈是否符合用户直觉。

产出:
- bug 清单:每条含复现步骤、截图、严重级(阻断/严重/一般/建议)。
- 零 bug 报告默认不可信:必须附"已走流程清单"(页面 × 操作 × 场景)证明覆盖完整,
  否则打回重测。
```

## D. 后端验收标准(常驻)

```
接口分两类,验收口径不同。所有测试必须真跑并贴原始输出(X passed / Y total),
"测试通过了"四个字不是证据。

【非 AI 接口】Jest e2e:
- 预期正常结果:典型输入 → 精确断言返回结构 + 副作用(数据库里真的写进去/改对了吗)。
- 预期异常结果:缺字段 / 类型错 / 越权 / 资源不存在 / 重复提交 / 边界值,
  每条断言确切的状态码与错误信息,而不是"只要报错就行"。

【AI 接口】带入复杂任务场景,测两种能力的极限:
- 决策能力:我们的提示词 + 上下文 + 约束条件,能否让 AI 在复杂场景下做对决定?
  要主动造难题:信息互相冲突、信息不全、用户意图模糊、需要多步推理的场景。
- 执行能力:AI 调用的工具与链路,执行后能否得到 AI 预期的结果?全链路真跑,
  不许 mock 中间环节。
- 防编造必测:故意喂缺失/单薄的数据,验证 AI 拒绝编造并明说缺什么,
  而不是硬编一个看起来合理的答案。
- 降级必测:主模型通道失败时用户看到什么?必须是优雅降级或明确报错,不许裸异常。

【范围规则】涉及前端的任务测前端,涉及后端的任务测后端,模块级任务前后端都测。
```
