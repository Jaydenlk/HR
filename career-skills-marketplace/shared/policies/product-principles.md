# 产品原则

## 原则 1: 标出处即呈现，少追问 (Source-then-show)

当用户信息不足时，skill 必须：
1. 明确说明缺失哪些关键信息
2. 不给无据的精确分数或强结论
3. 给出推断时**标清来源**（source_type + source_name + reason），不因为是推断就一律压成 low + 塞 cannot_determine
4. 明确哪些推断来自通用市场认知 / 行业惯例（`market_prior`），哪些是纯逻辑推理（`ai_inference`）
5. 给出当前仍可执行的下一步
6. 只追问最少必要问题，不把用户推入长问卷

### confidence 口径（底线 2：不连坐）

- confidence 反映**该维度 / 该子结论自身**的证据质量，**不再用全局 `min()` 连坐**——一个维度证据薄，不拖垮其它证据扎实的维度。
- 综合 summary 给"最关键维度的置信"，而非全局最低值。
- 只要标了来源（source_type + source_name + reason），就按"**标出处即呈现**"输出，不因为它是推断就强制降 low。

### cannot_determine 仅保留"非人工不可核实"项

只有**用户本人才知道的真实信息**才用 `cannot_determine`：
- 用户的真实经历 / 项目细节（简历里没写、只有本人知道）
- GPA / 排名等本人才能确认的数字
- 未公开的内部薪资档 / offer 细节

其余一律标出处即可，**不动辄 cannot_determine**。

**多源冲突 ≠ cannot_determine**：当多个来源数据打架时，**显式并列多方 + 标各自口径**，例如：

> 该岗供需比：脉脉口径约 2.09，智联口径约 17.2 份/岗。两口径统计范围不同，并列供你判断。

**不判 cannot_determine、不取中位数硬编**——并列呈现，把判断权交还用户。

### 字段映射

| 原则要求 | 使用现有字段 |
|---------|------------|
| 缺失（非人工不可核实） | `cannot_determine` + `follow_up_questions` |
| 普适市场认知 / 行业惯例 | `evidence_used` 中 source_type: `market_prior` |
| 纯逻辑推理 | `evidence_used` 中 source_type: `ai_inference` |
| 推断边界 | `risks` 中说明推断依赖的前提 |
| 可执行下一步 | `next_actions` |
| 该维度置信度 | 分维度 `confidence`（不全局连坐） |

## 原则 2: 出处-思考-观点分离 (Source-Reason-Opinion)

关键建议必须拆成三层：
- **Source / Evidence**: 依据来自用户输入、知识图谱、市场信息、来源审计、还是模型推理
- **Reasoning**: 为什么这些依据支持该判断
- **Opinion / Recommendation**: 最终建议、置信度、下一步

### 字段映射

| 层 | 使用现有字段 |
|----|------------|
| Source | `evidence_used[]` (每条标注 source_type) |
| Reasoning | `summary` (包含推理过程) |
| Opinion | `recommendations[]` + `confidence` + `next_actions[]` |

### 禁止行为

- "92 分，强烈推荐" 这种无证据强判断
- 信息不足时输出精确分数
- 把普适市场认知伪装成用户个性化结论
- 把小红书/牛客/公众号单一来源当成确定事实
- 用 "建议提升综合能力" 这种废话替代具体行动
- （反向同样禁止）把标了出处的合理推断一律压成 low + cannot_determine——这是**过度保守**，与上面的过度自信一样有害

## 原则 3: 时效信息当场联网 (Live-research-on-demand)

宿主（Claude Code CLI / Codex）**本就自带 WebSearch / WebFetch**。遇到**时效信息**时，当场搜、附 URL、标 `[实时·未核实·URL·日期]`，**而不是**用可能过时的训练知识硬答。

### 触发时效联网的信息类型

- 招聘时间窗 / 批次开放与截止
- 同岗竞争比 / 供需比
- 薪资行情 / 总包水平
- 公司近期动态（裁员、融资、组织调整、业务线变动）
- 行业冷热 / 赛道景气度
- 面经 / 真题 / 考点
- 政策（落户、应届身份、三方违约规则等）

### 规则

1. 命中上述类型 → **当场 WebSearch/WebFetch** → 附**本轮真实抓取**的 URL → 标 `[实时·未核实·URL·日期]`（"未核实"提醒用户单一来源仍需自行复核）。
2. **确实无网**（工具不可用 / 搜不到）→ 才降级用训练知识，并**显式说明**："以下为训练知识，可能已过时，建议你自行核实最新情况。"
3. **禁止伪造**：严禁编造权威 URL、来源标题、虚构日期。标 `[实时·URL]` 的 URL 必须本轮真 WebFetch 过；搜不到就老实写检索路径与空结果，不编。

## 固定标源标签（内联，生成时即绑定来源）

所有产出**句句有源**：在生成结论的当下就内联标注来源标签（优于事后补标）。固定枚举如下：

| 标签 | source_type | 含义 |
|------|-------------|------|
| `[据JD]` | `jd_text` | 来自用户提供的职位描述原文，须能定位原文片段 |
| `[据CV]` | `user_resume` | 来自用户简历原文，须能定位原文片段 |
| `[据知识库]` | `knowledge_graph` | 来自本仓知识库（公司库 / 标尺 / 职业预设等） |
| `[行业惯例]` | `market_prior` | 通用市场认知 / 行业惯例（"大厂校招通常 9 月开"这类共识） |
| `[推断]` | `ai_inference` | 纯逻辑推理（由已知前提推导，无外部来源） |
| `[实时·未核实·URL·日期]` | `web_search` | 本轮真实联网抓取，附 URL + 日期 |

`market_prior` vs `ai_inference` 区分：
- **`market_prior`（行业惯例）**：业内**普遍共识 / 通用市场认知**，非本次推理产物（如"互联网大厂普遍卡 985/211 简历关"）。
- **`ai_inference`（推断）**：由本次已知前提**逻辑推导**出的结论（如"你 JD 要求 3 年经验、你写了 1 年 → 推断硬性不达标"）。

## 通用防编造交付前 verify（三招）

凡"**基于用户原材料改写 / 扩写**"的产出（resume-tailor / behavioral-story-builder / personal-brand-builder / portfolio-project-advisor 等），交付前必须过三招：

### 招 1：确定性脚本兜底

对候选改写项跑 `../_career-skills-shared/scripts/check_fabrication.mjs`（子串 + 数字确定性校验）：

```
echo '{"resumeText":"<原材料>","suggestions":[<候选改写项>]}' | node ../_career-skills-shared/scripts/check_fabrication.mjs
```

- 退出码 0 = 无违规；1 = 有违规（按 `{"violations":[...]}` 下标降级 / 占位后重交付）；2 = 用法错。
- 规则 A：改进型 `original` 必须是原材料逐字子串；规则 B：`suggested` 里 `\d{2,}` 数字须在原材料逐字找到。

### 招 2：逐条引语回溯

逐条核对每条改写引语，抓两类编造：
- **无据数字**：原材料没有的量化指标（招 1 已机械兜底，此处人工复核占位符是否被悄悄填数）。
- **能力夸大**：动词 / 角色级别被拔高（如"参与"→"主导"、"协助"→"独立负责"），原材料不支持即回退。

### 招 3：locked rubric / 原材料防漂移

- 锁定标尺（rubric）的维度与满分**不因公司情报 / 联网信息而漂移**。
- 改写不得引入原材料里不存在的事实；新增内容只能走 `gap_advice`（标"面试穿帮风险"，需用户真实具备后再写）。
