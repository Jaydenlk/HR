# 示例 03 · source-conflict —— 简历与自述自相矛盾(后端开发)

## 场景说明

简历正文与用户口头自述/简历内部表述存在冲突:技能栏写「精通分布式」,但项目段落全是单机增删改查;
口头说「主导」了某系统,简历里却写「参与」。预期:**不沉默选边**,把冲突点摆出来、追问澄清,冲突不解决前相关维度据**可证实的较低事实**给分。

---

## 输入

```yaml
target_profession: 后端开发        # 命中 professions/backend-campus.md
difficulty_tier: standard
resume_text: |
  王同学 / 计算机 / 应届2026
  技能:精通分布式系统、精通高并发架构、精通微服务
  项目:图书管理系统(校内)
    - 参与后端开发,用 Spring Boot 实现图书的增删改查与借还登记
  实习:某小型外包公司,做企业官网的表单提交后端
用户自述:这个图书系统其实是我一个人主导设计的,分布式那块我很熟。
```

---

## 期望 output 要点

- `confidence`: **medium**(信息可解析但存在内部矛盾,需澄清才能定档)
- `risks`(**非空**):明确列出冲突点——
  - 「技能栏自称『精通分布式/高并发/微服务』,但唯一项目是单机增删改查、实习是表单后端,**简历证据不支撑该自评等级**」
  - 「项目写『参与』,自述称『一人主导』,**主导/参与影响系统设计与工程实践维度评分**,口径不一致」
- `diagnosis.dimensions`:
  - `系统设计与分布式能力`:**按可证实的较低事实给分**(项目无任何并发/缓存/分布式设计 → 命中「CRUD仔」,低档),`why` 点明「技能自评与项目证据矛盾,采信项目实证」,**不因『精通』字样给高分**
  - `编程语言与语言底层`:据实评(只列栈、无深度展开)
  - 其余维度同理据实
  - `evidenceFound` 只收**简历白纸黑字**的事实;自述部分进 `follow_up_questions`,不直接当证据计分
- `follow_up_questions`:
  - 「『精通分布式/高并发』具体落在哪个项目的哪个设计决策上?能举一个并发场景的取舍吗?」(关系系统设计维度)
  - 「图书系统你是主导还是参与?简历写『参与』、你说『主导』,以哪个为准?」(关系系统设计/工程实践维度)
- `diagnosis.conventionChecks`:项目可信度=`warn`/`fail`(技能自评与项目脱节);技术栈分档=`warn`(滥用「精通」)
- `interviewHooks`:必含一条针对该矛盾——「简历写精通分布式,面试官会让你现场设计一个高并发场景」,`prepDirection` 引导**据实校准自评**而非教如何圆谎
- `honesty_boundary`:声明存在自评与证据的矛盾、本次按可证实事实评分、待澄清

---

## rationale(为什么这样判)

冲突案例的考点是 **source-reason-opinion(出处→思考→观点)+ 不替用户圆谎**:遇到「自称 vs 实证」矛盾,既不盲信高自评、也不直接判定造假,而是**摆出冲突 + 采信可证实的较低事实 + 追问澄清**。
`evidenceFound` 只采信简历明文,口头自述归入 `follow_up_questions`;这样既诚实又给用户解释机会。
改写阶段对「精通分布式」这类无项目支撑的自评,只能走 `gap_advice`(建议先有真实分布式项目再写),**绝不**在改进型里替用户坐实。
