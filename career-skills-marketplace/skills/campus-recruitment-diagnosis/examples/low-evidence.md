# 示例 02 · low-evidence —— 普通校 + 弱背景 + 信息不足(后端开发)

## 场景说明

双非本科,简历只有课程项目和一句技能列表,**完全无量化数字、无实习、无 GitHub 链接、无竞赛**。
信息不足以支撑精确评分。预期:`confidence` 降级、`follow_up_questions` 非空、低分维度据实给低档、不编造也不打压过头。

---

## 输入

```yaml
target_profession: 后端开发        # 命中 professions/backend-campus.md
difficulty_tier: standard
resume_text: |
  李同学 / 软件工程 / 应届2026
  教育:某双非本科 软件工程
  项目:学生成绩管理系统(课程作业)
    - 用 Spring Boot 做了增删改查,前端用 Vue
  技能:熟悉 Java、熟悉 MySQL、熟悉 Spring Boot、熟悉 Redis
```

---

## 期望 output 要点

- `confidence`: **low**(职业命中但关键信息严重缺失:无量化、无实习、无项目可信度背书)
- `diagnosis.total_score`:仍可给出(各维之和,应落在低位),但 `summary` 须点明信息不足、评估偏定性
- `diagnosis.dimensions`(5 维,与标尺一致):
  - `编程语言与语言底层`:命中反模式「语言搬运工」——只列技术栈、说不出 JVM/IoC 原理,低档
  - `计算机基础`:无任何场景闭环,低档
  - `系统设计与分布式能力`:命中反模式「CRUD仔」——项目全是增删改查,无并发/缓存/异步设计,极低分
  - `工程实践深度`:命中反模式「课程仔」——仅课程作业、无生产环境/GitHub,极低分
  - `算法与数据结构`:简历完全无佐证(无刷题量/竞赛),极低分;`gap` 列出「未体现刷题量/竞赛」
  - 每维 `evidenceFound` 极少或为 `[]`,`gap` 据实列缺口;**不得**臆造「应该有但没写」的能力
- `diagnosis.conventionChecks`:技术栈分档=`fail`(全写「熟悉」,违反精通/熟悉/了解三档)、项目可信度=`fail`(无 GitHub、无大厂实习、无业务数字)、竞赛=`warn`(简历未提)
- `follow_up_questions`(**非空**,每问附「为何需要」,≤2 问/轮):
  - 「这个成绩管理系统有没有上线/真实用户?你在其中主导还是参与?」(关系工程实践与系统设计评分)
  - 「有没有刷题量、竞赛、或任何带数字的项目成果?」(关系算法维度与可信度)
- `cannot_determine`:列出因缺数据无法判断的项(如「实际工程深度」「算法真实水平」)
- `honesty_boundary`:声明信息不足、评估偏定性、补齐上述信息后可重评

---

## rationale(为什么这样判)

弱背景案例的考点是 **ask-before-judging + 据实不夸大**:信息不足时**先追问**而非直接拍死,但追问到顶(≤2 轮)仍缺就用现有信息出结论并把 `confidence` 标 `low`。
低分要落到反模式名(CRUD仔/课程仔/语言搬运工)而非空泛差评;`gap` 只列简历**确实没有**的东西,绝不臆造。
这区别于 bad-input:这里简历**可解析、职业可命中**,只是证据不足 → 给低分 + 降置信度 + 追问;而非拒绝评分。
