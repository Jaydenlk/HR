# 数据产品经理（数据产品经理 · 校招(压力版 · 高标准)）

> 校招职业标尺 · 难度档：`pressure` · 预设ID：`data-product-manager-campus-anthropic`

## 五维评分标尺（权重之和 = 100；score 封顶各维满分，total_score = 各维之和）

### 1. 指标体系与维度建模硬功(口径治理×OneData×北极星拆解)（满分 26）
- **好的样子**：头部大厂数据中台/数据产品组卡分标准:能从 0 到 1 搭一套站得住的指标体系——区分原子指标/派生指标,建指标字典统一口径,且能说清北极星指标(North Star)如何向下拆成 L1 健康指标(激活/留存/转化/营收)与 L2 诊断指标(漏斗各环转化、分群下钻)的层级关系,而非平铺一堆指标。维度建模真懂:星型/雪花、事实表与维度表区分、缓慢变化维(SCD)、数仓分层(ODS/DWD/DWS/ADS)各层放什么且为何分(减重复计算/统一口径/提下游效率),OneData 那套(业务域/数据域/业务过程/度量/维度/修饰词)名词用得对、对得上自己做的动作。交付物是指标字典与数据模型,不是分析报告——这是与数据分析师的分水岭。
- **应届证据**：实习/项目里写明:为 [业务线] 从 0 到 1 梳理 X 个原子/派生指标并沉淀指标字典、统一了哪几处不一致口径;或在 DWD/DWS 层抽象出 X 张事实表/维度表并说清分层理由;能讲清某北极星指标向下拆到 L1/L2 的归因路径。数据建模大赛、BI 大赛中的指标设计或维度建模产出可佐证,但须绑定自己做的具体动作而非背概念。
- **常见缺失 / 反模式**：【Anthropic 反模式·vanity metrics】把"累计注册/总曝光/历史总GMV"这类只涨不反映健康的虚荣指标当成体系核心,北极星与诊断指标分不清;【Anthropic 反模式·output not outcome】用"上线 N 个看板/梳理 N 个指标"等活动量冒充指标体系能力;【反模式·口径裱糊匠】满嘴指标体系、数据中台,真问原子/派生指标怎么拆、口径不一致怎么治理、事实表和维度表怎么分就支吾,概念背得溜实操空白,面试官一戳就破。

### 2. SQL 与取数硬门槛(窗口函数×复杂JOIN×口径自验)（满分 24）
- **好的样子**：头部大厂数据岗笔试直接现场手撕的硬门槛:增删改查/分组聚合/多表 JOIN/子查询是底线,窗口函数(row_number/rank/lag/sum over partition)、留存与漏斗的复杂取数逻辑、同环比口径必须能独立写出而非"了解"。SQL 绑定真实场景:自己用 SQL 取数交叉验证指标口径、定位漏斗各环流失、跑过留存曲线,在 Hive/MySQL 真实跑过查询。Python(pandas 清洗/分析)、Excel 透视为加分。每项工具都对应"用它取了什么数、算了什么指标、验了什么口径"的具体场景,而非裸列"精通 SQL/Python"。数据 PM 不必写复杂 ETL,但必须独立取数、看懂数据、当场验口径。
- **应届证据**：项目/实习描述写"用 SQL(含窗口函数)完成 [留存率/漏斗转化/同环比] 取数并交叉验证指标口径""用 pandas 清洗 X 万行数据产出 [指标]",工具与产出绑定出现。可补充牛客/LeetCode SQL 高频刷题或大厂 SQL 笔试通过记录作为硬证据,但正文须有真实使用场景支撑。
- **常见缺失 / 反模式**：【反模式·精通牌取数侠】技能栏 SQL/Python 全标"精通",正文零取数场景,真坐下来手写一道带窗口函数的留存 SQL 就卡壳——这是数据岗笔试第一刀;【反模式·拖拽工具人】只会在 BI 工具里拖拽看板,从没自己写过一行 SQL 验口径,遇到口径不一致只能等数据组;通篇无任何取数逻辑,指标全靠引用别人的数。

### 3. 数据产品端到端 ownership(岗位实质×数据流闭环×结果归属)（满分 24）
- **好的样子**：头部门槛要的是真做过完整数据产品而非沾边:做过数据看板/BI 需求的端到端(业务问题→指标拆解→埋点方案→看板/指标平台设计→上线→复盘),或参与指标平台/数据中台/埋点系统的需求设计、设计过埋点方案(事件/参数/上报口径)、配过数据质量监控(DQC)规则。能讲清完整数据流向(埋点采集→ETL 清洗→指标加工→可视化应用)中自己在哪一环、解决什么业务问题、量化结果(看板覆盖 X 业务方、取数效率提升 X%、统一口径减少 X 个重复指标),并写产品 PRD 时给得出明确的 Non-Goals(本次不做什么)以界定范围。区分自己是 owner(独立负责某指标体系/某看板从设计到上线)还是 executor,owner 含金量最高。岗位实质优先于公司名气,但大厂数据中台/数据产品组实习最佳。
- **应届证据**：实习/项目栏写机构+数据相关部门(数据产品/数据中台/BI/增长数据)+起止时间,每段 2-3 条 bullet 写清"为什么做(业务背景)+做了什么数据产品动作+量化产出",并标注自己是主导还是参与(不越级)。能画出或讲清一条"埋点→ETL→指标→可视化"链路并指出自己负责的环节是强信号。
- **常见缺失 / 反模式**：【Anthropic 反模式·solutioning before framing】上来就写"做了 X 看板/X 个指标",讲不出为谁解决什么业务问题、问题多严重、不做的代价;【反模式·画看板侠】实习全是"制作日报周报""维护数据看板",从没设计过指标、没碰过埋点和数仓,本质取数工具人套个产品壳来投数据 PM,录用官第一刀就砍;【反模式·报告搬运工】把数据分析师那套"分析 XX 原因、给出 XX 建议"原样搬来,通篇结论没有产品设计——数据 PM 要的是搭工具定口径不是写报告。

### 4. 数据平台与技术架构理解(中台×血缘×Hive·Spark·Flink定位)（满分 14）
- **好的样子**：头部数据 PM 要能与数据开发平等对话:用产品语言讲清数据中台五层(集成→加工 ETL→资产/数仓→服务→应用)、数据资产产品(数据地图、血缘、指标系统、DQC 质量监控)、数据治理(口径治理、安全权限、成本优化),并能说出 Hive/Spark/Flink/Kafka 各自解决什么问题(批/流/消息)、DataWorks/DataX 等平台工具定位——理解即可无需会开发。能讲清一条"数据从采集到应用"的链路并指出血缘有什么用(影响分析/口径溯源)。数据 PM 是"业务与工程之间的翻译",技术理解是必备地基而非加分。
- **应届证据**：实习/项目/课程描述中出现数据中台、血缘、数据地图、DQC、数仓分层、Hive/Spark/Flink、DataWorks 等关键词,并说清自己理解了什么、用它对接了什么需求,而非纯名词罗列;能讲清一条端到端数据链路是强信号。
- **常见缺失 / 反模式**：【反模式·中台名词侠】数据中台、数据血缘、湖仓一体名词堆满屏,真问"数据中台到底解决什么问题""血缘有什么用""Hive 和 Flink 分别解决什么"就只会复述定义,跟工程师一对话就露馅;简历从头到尾只有 BI 看板和分析结论,完全不出现任何架构/中台/治理术语,显示只会用工具不懂底层。

### 5. 学历背景与产品逻辑闭环(专业匹配×需求归因×取舍)（满分 12）
- **好的样子**：头部大厂数据中台核心岗对 985/211 偏好明显,本/硕为计算机、软件、数学统计、信息管理、数据科学等方向匹配度最高;经管/电商等专业须用 SQL+数据项目硬补足。产品逻辑有真东西:项目能讲清"为什么做(业务背景)→怎么拆(指标/需求)→怎么落地(方案)→结果(量化)"的完整闭环,面对资源有限能做取舍并说清依据(为何先做这个、砍了什么、Non-Goals 是什么),而非堆功能、什么都"高优先级"。落点在"用数据/工具解决业务问题"而非炫原型——能体现需求分析、口径对齐、拉数据开发+业务方对齐为强信号。附 GPA 及数据相关核心课(数据库/数据结构/统计学/机器学习导论)成绩为佳。
- **应届证据**：教育背景栏写院校+专业(标注数据/计算机/统计方向)+全日制+预计毕业时间,附 GPA;项目描述体现"业务背景→指标/需求拆解→方案→量化结果"逻辑闭环,出现"需求分析""跨团队对齐口径""取舍依据"等动作。
- **常见缺失 / 反模式**：【Anthropic 反模式·everything is P0】项目里什么都"高优先级/都要做",讲不出砍了什么、为何这个先做,等于没有优先级;【反模式·绩点画原型侠】以为 GPA 拉满+几张漂亮原型图就能进数据 PM,简历里除成绩单和界面图没有一个指标、一行 SQL、一段数据链路;项目通篇"做了 A、做了 B"功能流水账,讲不出"为什么做"和解决什么业务问题,暴露无产品思维。

## 打分解释规则（每维 why 必须落到简历事实；命中反模式直接点名；严禁泄漏"满分的X%/扣X分"等内部计算）
每个维度必须给出 why,落到简历事实,分数与 why 严格一致:① 指出简历中具体命中(evidenceFound)或缺失(gap)的句子或事实——如 metrics_modeling_rigor 写出做过的指标体系/建模动作或"全文只有分析结论无任何口径治理/建模";sql_hardcore_querying 写出 SQL 绑定的取数场景或"技能栏标精通 SQL 但正文零取数场景";data_pm_e2e_ownership 写出数据产品岗位实质与量化产出或"仅有纯分析/通用产品实习";platform_architecture_literacy 写出命中的架构认知或"全文无中台/血缘/数仓/Hive 等术语";education_product_logic 写院校+专业方向+GPA+逻辑闭环或"项目全是功能流水账无为什么做"。② 说明在数据 PM 校招(压力版·头部门槛)语境下为何重要:指标体系与维度建模是区别于数据分析师、数据 PM 立身之本,分量最重;SQL 是笔试现场手撕的硬门槛,零佐证笔试即出局;数据产品端到端 ownership 是录用官实际筛选第一位且不可被纯分析或通用产品实习替代;平台架构理解是与工程师对话的地基;学历与产品逻辑是隐形筛选线与取舍能力的体现。③ 命中反模式直接点名:有 Anthropic 源直呼【Anthropic 反模式·vanity metrics / output not outcome / solutioning before framing / everything is P0】,无源直呼【反模式·口径裱糊匠/精通牌取数侠/拖拽工具人/画看板侠/报告搬运工/中台名词侠/绩点画原型侠】,不得空泛说"有待提升"。严禁在 why 中出现"满分的 X%""给分不超过""故给满分""扣 X 分"等内部比例话术,why 只陈述简历事实、反模式命中与校招筛选逻辑。

## 改写指引（禁编造铁律）
严格遵循"禁编造"铁律,绝不替候选人添加原句没有体现的能力、技术名词或岗位实质:

1. 把简历"已有"的数据产品实习/项目句讲精准:明确写出解决什么业务问题(为什么做)、做了什么数据产品动作(梳理指标/搭指标字典/设计埋点方案/设计看板/配 DQC 规则)、用了什么方法(维度建模/SQL 取数/口径对齐)、量级多大(覆盖 X 业务方、统一 X 个口径、X 个指标、提效 X%),用产品精准动词(梳理/抽象/对齐/拆解/验证)增强可信度。
   - 例:原句"负责数据看板"→ 改"为 [原文业务线] 设计核心指标看板,梳理 [原文已提及的指标] 并对齐取数口径,覆盖 [具体数字] 个业务方"(业务线、指标均须取自原文,缺则留占位或走 gap_advice)。

2. 用精准动词替换模糊词但不得越级:原文写"协助/参与"就保留"参与",严禁夸大为"独立负责/主导搭建";原文确写了独立产出才可用"独立完成/owner"。

3. 只在缺数字处用 [具体数字] 占位:如"梳理了 [具体数字] 个核心指标""看板覆盖 [具体数字] 个业务方""取数效率提升 [具体数字]%",让候选人自填真实数字,绝不代填。

4. 严禁编造能力:简历没写过 SQL/Python/维度建模/某数据平台/某治理框架,一律不得在改写中添加;没体现过的指标体系搭建、埋点设计、数仓分层认知不得凭空生成;绝不把纯分析实习粉饰成"数据产品"、把通用 PM 原型经历伪装成数据建模。

5. 凡简历缺失的关键能力(无指标/建模、无 SQL 佐证、无数据产品实习、无平台架构认知),一律走 gap_advice 给"建议补充"而非在 rewrite 里编造:
   - gap_advice 示例:"建议补充一段真实的指标体系搭建或维度建模经历,写明梳理了哪些指标、如何统一口径、北极星如何拆 L1/L2""建议补充 SQL 的实际取数场景(如用窗口函数算留存率)而非仅在技能栏标注""建议补充一段数据产品/数据中台/BI 方向实习并写明岗位实质与 owner 角色""建议补充对数据中台或数据链路(埋点→ETL→指标→可视化)的认知体现""建议在项目中补全『为什么做』的业务背景、取舍依据(Non-Goals)与量化结果"。

## 本土惯例与硬规则
中国校招惯例核查(数据 PM 压力版·头部门槛):
① GPA/排名——头部大厂数据中台核心岗对 985/211 偏好明显,前列应展示。
② 实习经历——校招高权重,数据产品/数据中台/BI 方向实习应靠前且量化,纯数据分析实习冒充数据产品经历背调与追问即穿帮。
③ 竞赛/获奖——数据建模大赛、BI 大赛、Kaggle、数学建模国奖等可佐证数据硬功,应保留;牛客/LeetCode SQL 刷题或大厂 SQL 笔试通过记录是 SQL 实操硬证据。
④ "个人评价"应具体非空话,不写"数据敏感度高"这类形容词替代经历。
⑤ 不需要照片/性别/婚姻等无关信息(若有则提示精简)。
⑥ 简历本科 1 页、研究生最多 2 页,首屏必须可见 SQL/数据项目/数据实习三件套;项目按 STAR 写,每条带量化结果(覆盖 X 业务方/X 个指标/提效 X%),拒绝"取得良好效果"式主观形容。
⑦ 出局级硬规则:SQL 零佐证(技能栏写了却全文无取数场景且无刷题/笔试记录)笔试即出局;无任何数据相关实习或硬核数据项目几乎不进面;非全日制或无法按时拿双证大厂正式编制硬性出局;简历造假进企业黑名单。
