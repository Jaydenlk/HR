# 使用示例

以下 6 个示例均为合成场景，用于展示系统在真实求职情境下的行为方式。所有人名、学校、公司均为虚构或脱敏处理。

---

## 示例 1：应届生投字节后端

**场景**：某 985 高校计算机专业应届生，有两段后端实习经历，投递字节跳动飞书团队后端工程师岗位。

**用户输入**：
> 我是 CS 应届，两段 Go 后端实习，一段在 200 人规模的 SaaS 创业公司做 API 网关开发，一段在外企做微服务迁移。我想投字节飞书后端，这个 JD（文本见附件）。

**调用的 skill 链**：
1. `jd-analyzer` — 解析 JD，识别核心技术栈（Go、gRPC、分布式系统）和隐性要求（高并发经验、大规模系统设计）
2. `profile-builder` — 提取用户能力画像：Go 熟练、API 网关经验、微服务迁移、无大厂或超大规模系统经验
3. `match-diagnosis` — 输出多维匹配分析
4. `resume-tailor` — 针对匹配差距重组简历表达

**输出示例**：
```
匹配诊断（career-principal 汇总）

核心技术栈匹配：高（Go + gRPC + 微服务 均有实证）
规模经验匹配：中（最大项目为 200 人公司，JD 要求大规模高并发）
软技能信号：中（跨团队协作有描述，但无量化数据）

主要差距：分布式系统设计（如一致性算法、跨 IDC 部署）
建议：在简历中补充 API 网关的实际 QPS 数字、微服务迁移影响的服务数量

置信度：中
依据：字节跳动在知识图谱中有记录，JD 解析完整；规模经验差距判断基于 JD 原文措辞，非推测。
```

**为什么可信**：系统的差距判断直接引用了 JD 原文关键词，没有在用户简历中添加未提及的技术。

## 示例 2：双非文科背景转产品

**场景**：双非院校中文系大三学生，有一段微信公众号运营经历，想转互联网产品经理。

**用户输入**：
> 我是双非学校中文系大三，做过一年半的微信公众号运营，涨粉从 3000 到 28000，现在想转产品，有机会吗？

**调用的 skill 链**：
1. `profile-builder` — 提取画像：内容创作、用户增长运营、数据意识（提及具体涨粉数字），无产品设计/原型/需求文档经验
2. `match-diagnosis` — 与产品管理岗类别标准对比
3. `career-principal` — 综合输出转行可行性评估和路径建议

**输出示例**：
```
转行可行性评估

可迁移能力：用户视角（内容运营培养）、数据意识（涨粉数字说明你关注增长指标）
主要差距：产品设计工具（Axure/Figma）、需求文档写作、用研方法论
风险信号：无实习项目背书，双非背景在大厂简历筛选中会有初筛压力

建议路径：
1. 在校期间完成 1 个产品实习（校内创业项目或外部实习均可）
2. 输出 2-3 份完整 PRD 作品集
3. 目标公司优先考虑中小规模互联网公司，积累后再投一线大厂

置信度：中（产品转行路径有规律可循，但个体差异大）
```

**为什么可信**：系统列明了画像中存在的能力证据，差距判断来自用户实际提供的信息，没有因"文科"标签做负面假设。

## 示例 3：运营岗小红书面经准备（附"无近期数据"提示）

**场景**：用户准备小红书内容运营岗位面试，希望了解公司和岗位信息。

**用户输入**：
> 我下周要面小红书的内容运营，帮我梳理一下这个岗位的面试重点，以及小红书这家公司的关键信息。

**调用的 skill 链**：
1. `jd-analyzer`（基于用户描述构建岗位标准）
2. `source-quality-auditor`（评估知识图谱中小红书数据的时效性）
3. `career-principal`（汇总输出，附注数据局限）

**输出示例**：
```
岗位面试重点（基于内容运营岗类别通用标准）

常见考察维度：
- 内容策略与选题方法论
- 数据驱动运营（发布时间、互动率、转化路径）
- 用户增长与社区生态理解
- 小红书平台机制认知（推荐算法、流量结构）

小红书公司信息（知识图谱记录）

[数据时效提示] 我的知识图谱中有小红书的基础记录，但数据构建时间有限，无法保证当前状态的准确性。以下内容供参考，建议同步核实：

行业定位：内容社区 + 电商平台
核心业务：UGC 内容生态、品牌广告、直播电商
规模阶段：知识图谱记录阶段为成熟期，具体最新融资/人员规模请核实

建议补充来源：牛客网近 3 个月面经、脉脉公司动态、官方公众号
```

**为什么可信**：系统主动标注了数据时效局限，没有把旧信息包装成"最新情报"输出。

## 示例 4：英文 JD + 中文简历的跨语言处理

**场景**：用户手持中文简历，目标岗位 JD 为英文（外资公司），希望进行匹配分析。

**用户输入**：
> 我的简历是中文的（见附件），JD 是英文的：「Senior Data Analyst, 5+ years exp, proficient in SQL/Python, experience with A/B testing and product analytics, cross-functional collaboration」，帮我分析匹配度。

**调用的 skill 链**：
1. `jd-analyzer` — 解析英文 JD，映射为内部标准字段（技能要求、经验要求、软技能）
2. `profile-builder` — 从中文简历提取画像，保留原语言证据
3. `match-diagnosis` — 跨语言对比，输出匹配结果（结果以中文呈现）
4. `resume-tailor` — 提供英文简历改写建议（如用户需要）

**输出示例**：
```
匹配分析（中文简历 vs 英文 JD）

JD 核心要求 → 你的画像对应情况：
- SQL/Python 熟练 → 匹配（简历中有 3 个数据分析项目，工具明确）
- A/B 测试经验 → 部分匹配（有数据实验描述，但未明确提"A/B test"）
- 跨部门协作 → 需补充（简历中有协作场景，但无具体描述）
- 5 年以上经验 → 待确认（简历显示 3 年，请告知是否含兼职/实习）

建议：将简历中"数据实验"改写为英文语境惯用表达"ran A/B tests to validate hypothesis"，以提升 ATS 识别率。

置信度：中（基于你提供的简历文本，未联网核实 JD 发布方实际要求）
```

**为什么可信**：系统没有假设中文词汇和英文术语一定等价，明确标注了需要用户确认的信息。

## 示例 5：Offer 北京 vs 上海对比（含生活成本）

**场景**：用户手持两个 offer，需要做选择决策。

**用户输入**：
> 我拿了两个 offer：一是北京某 AI 独角兽，base 28k/月，12 薪，有期权；二是上海某外资银行，base 30k/月，15 薪，无期权。我老家在武汉，不介意两个城市。帮我做个对比。

**调用的 skill 链**：
1. `jd-analyzer`（构建两个岗位的基本属性）
2. `source-quality-auditor`（评估知识图谱中两家公司的数据质量）
3. `career-principal`（输出多维对比框架，不替用户做决定）

**输出示例**：
```
Offer 多维对比

维度 1：年度现金收入（估算）
北京 AI 独角兽：28k × 12 = 336k（期权价值不计入现金，需单独评估）
上海外资银行：30k × 15 = 450k

维度 2：生活成本调整（参考公开数据，非实时）
北京一室一厅租金参考：6,000-10,000/月（区域差异大）
上海一室一厅租金参考：6,500-11,000/月（区域差异大）
两城生活成本总体相近，上海略高

维度 3：职业发展方向
AI 独角兽：高增长赛道，期权有不确定性但上限高，适合接受波动的人
外资银行：相对稳定，品牌背书强，适合注重确定性收益的人

维度 4：期权评估
AI 独角兽期权需关注：当前估值、锁定期、条款中的对赌条款。建议入职前要求公司提供期权协议全文。

[系统不替你做最终决定] 以上是结构化分析框架。城市选择、行业偏好和个人风险偏好的权重，由你自己打分。

置信度：中（公司背景基于知识图谱，生活成本数据参考公开资料，薪资比较基于你提供的数字）
```

**为什么可信**：系统给出对比框架而非结论，明确了生活成本数据的来源局限，并提醒用户注意期权合同细节。

## 示例 6：证据不足时拒绝高置信判断

**场景**：用户询问的公司不在知识图谱中，信息来源单一。

**用户输入**：
> 我朋友说某家叫「晨星未来」的公司挺不错的，是做 AI 教育的，想去试试，你觉得这家公司怎么样？

**调用的 skill 链**：
1. `source-quality-auditor` — 评估输入信息：来源为单一口头信息，无法核实
2. `career-principal` — 触发低置信降级输出

**输出示例**：
```
[知识图谱未覆盖]

「晨星未来」不在我当前的知识图谱中（知识图谱目前覆盖 50 家企业，以头部互联网和部分知名外资为主）。

你的信息来源为朋友口头转述，这属于单一非正式来源，我无法基于此做出任何关于这家公司的判断。

如果你想继续评估这家公司，建议收集以下信息再回来：
1. 工商注册信息（天眼查/企查查）：成立时间、融资记录、股权结构
2. JD 原文：用于岗位分析
3. 招聘平台评价：Boss直聘、脉脉等平台上的员工评价

在获得上述信息之前，我无法给出高置信的公司评估。这是系统的硬性约束，不是保守——用编造的信息帮你做决定反而是更大的风险。

置信度：极低（来源不足，不适合输出判断）
```

**为什么可信**：系统明确说明了为什么无法输出判断，并提供了用户可以自行收集信息的具体路径，而非给出一个听起来合理但无根据的答案。
