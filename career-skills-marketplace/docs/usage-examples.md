# 使用示例

以下 10 个示例均为合成场景，展示系统在真实求职情境下的行为。所有人名、学校、公司（晨星未来等）均为虚构或脱敏处理。

---

## 示例 1：JD 分析 — 帮我看这个字节后端 JD

**用户输入**：
> 帮我看这个字节后端 JD（文本见附件）。

**调用的 skill**：`jd-analyzer`

**关键输出**（缩略）：
```
JD 分析结果

核心技术栈：Go、gRPC、分布式存储、高并发系统设计
经验门槛：3 年以上相关经验，有大规模系统经历优先
隐性要求信号：JD 措辞含"百亿级数据"，暗示对大规模场景有真实诉求
风险信号：无明确薪资区间，建议面试前向 HR 确认 Band 范围

risk_signals: ["薪资未公示", "大规模经验要求措辞强烈"]
confidence: high
evidence_used: ["JD 原文"]
```

**置信度**：high（基于 JD 原文解析，无推测）

**为什么可信**：所有结论均直接引用 JD 原文关键词，不做超出文本的推断。

## 示例 2：简历改写 — 帮我按这个 JD 改简历

**用户输入**：
> 我简历里有这段经历（文本见附件），JD 要求分布式系统设计经验，帮我改写这段表达。

**调用的 skill**：`profile-builder` → `jd-analyzer` → `resume-tailor`

**关键输出**（缩略）：
```
简历改写建议

原句：「参与了微服务架构改造项目」
改写后：「负责微服务架构改造中 API 网关模块设计，优化后服务调用延迟降低 40%」

fabrication_check: PASS（改写内容完全来自用户提供的原始简历，未添加任何虚构数据）
modifications: ["补充了量化指标（40% 来自用户附件第 3 段）", "替换了被动句式"]
confidence: high
```

**置信度**：high（改写内容可追溯至用户提供的原文）

**为什么可信**：`fabrication_check: PASS` 表示系统验证了所有改写内容均有原文依据，无编造。

## 示例 3：匹配诊断 — 我适合这个岗位吗

**用户输入**：
> 我是 3 年 Java 后端，做过电商订单系统，适合这个字节广告系统后端岗位吗？

**调用的 skill**：`profile-builder` → `jd-analyzer` → `match-diagnosis`

**关键输出**（缩略）：
```
匹配诊断

综合匹配分：72 / 100

维度明细：
- 技术栈匹配：65（Java 匹配，但 JD 偏 Go；广告系统与电商场景有差距）
- 规模经验匹配：80（电商订单系统有高并发经验，与广告系统部分重合）
- 领域知识匹配：55（广告检索、竞价机制未在简历中出现）

主要差距：广告系统领域知识（RTB、CPM、归因模型）
建议：面试前了解广告系统基本架构；简历中突出订单系统的 QPS 数字

confidence: medium
evidence_used: ["用户简历描述", "JD 原文", "role-taxonomy: backend-engineer"]
```

**置信度**：medium（领域知识差距判断基于用户输入，无法从外部核实）

**为什么可信**：每个维度分数都有独立的依据说明，不是黑箱总分。

## 示例 4：Offer 对比 — 字节 vs 银行，选哪个

**用户输入**：
> 字节飞书后端 offer：base 28k，12 薪，有期权。某国有银行科技岗：base 22k，15 薪，无期权，五险一金基数全额。帮我对比。

**调用的 skill**：`offer-comparator`

**关键输出**（缩略）：
```
Offer 多维对比

年度现金（估算）：
- 字节：28,000 × 12 = 336,000（期权价值不计入现金）
- 银行：22,000 × 15 = 330,000（差距约 0.6%）

时薪换算（按 251 工作日 × 8h）：
- 字节：约 167 元/小时（不含加班）
- 银行：约 164 元/小时

期权评估：
- 字节期权需核实：当前估值基准、锁定期（通常 4 年）、稀释条款
- 建议索取期权协议全文再签署

社保差异：
- 银行五险一金全额基数，长期复利效应显著（约每年多缴 3 万+）

[系统不替你做最终决定] 职业方向偏好、加班容忍度、风险偏好由你自行权重打分。

confidence: medium
evidence_used: ["用户提供数字", "city-industry-fit: 北京"]
```

**置信度**：medium（现金计算确定，期权评估和社保估算需用户核实具体条款）

**为什么可信**：区分了确定数字（现金）和不确定因素（期权、社保细节），给出可操作的核实步骤。

## 示例 6：面试准备 — 腾讯产品经理一面怎么准备

**用户输入**：
> 我下周一面腾讯产品经理（to-C 方向），帮我梳理准备重点。

**调用的 skill**：`interview-intelligence`

**关键输出**（缩略）：
```
腾讯 产品经理 一面准备指南

面试流程（知识图谱记录）：
- 一面通常为 HR 初筛或基础素质面，重点考察：动机、基本逻辑、沟通表达

常见问题类型：
1. 自我介绍（建议 2 分钟，突出核心经历和为什么选腾讯）
2. 为什么做产品、为什么来腾讯（动机类）
3. 用过哪个产品，说说改进建议（产品感知类）
4. 讲一个你主导的项目（执行力类）

腾讯产品面特点：
- 注重用户同理心和数据意识
- to-C 岗位会考察对微信/QQ 生态的理解

[数据时效提示] 腾讯在知识图谱中有记录（Tier 1），但面试流程可能随团队变化。建议同步查阅牛客近 3 个月面经。

confidence: medium
evidence_used: ["knowledge-graph: 腾讯 Tier 1", "interview-taxonomy: product-manager"]
```

**置信度**：medium（知识图谱覆盖，但面试题随时间变化，建议核实近期面经）

**为什么可信**：区分了知识图谱记录内容和需要用户核实的时效内容。

## 示例 8：来源审查 — 这个面经可信吗

**用户输入**：
> 我在牛客上看到一个字节 2024 年 3 月的 Go 后端面经，说是三面都考了系统设计，这个可信吗？

**调用的 skill**：`source-quality-auditor`

**关键输出**（缩略）：
```
来源质量审查

来源类型：牛客网用户发帖
发布时间：2024 年 3 月（距今约 14 个月）
核实状态：无法独立核实

来源评级：B
- 优点：有具体时间节点，牛客面经有一定社区验证机制
- 缺点：单一来源，无法确认发帖者身份和岗位层级
- 时效性：14 个月以上的面经，字节面试结构可能已调整

freshness: 2024-03（超过 12 个月，标记为需核实）
verification: 建议搜索同期（2025 年）的 Go 后端字节面经做对比
```

**置信度**：medium（来源可信度一般，标注了衰减风险）

**为什么可信**：系统给出结构化评分而非简单"可信/不可信"，明确说明了每项判断的依据。

## 示例 9：职业路径 — 后端转产品可行吗

**用户输入**：
> 我做了 4 年 Go 后端，现在想转产品经理，可行吗？

**调用的 skill**：`career-path-planner` → `role-transition-advisor`

**关键输出**（缩略）：
```
路径可行性评估

后端工程师 → 产品经理（to-B 技术产品方向）

可迁移能力：
- 技术理解深度（优势：能与研发高效沟通，理解技术可行性边界）
- 系统思维（有助于功能拆解和数据流梳理）

主要技能差距：
- 用户研究方法论（访谈、问卷设计）
- PRD 写作规范
- 商业感知（定价、竞品分析）

建议路径（18-24 个月）：
1. 在现岗位中主动承担内部工具需求文档工作（0-6 个月）
2. 输出 2 份完整 PRD 作品集（针对自己熟悉的业务场景）
3. 目标：技术产品经理（TP）方向，而非纯 to-C 消费品产品

风险提示：纯 to-C 产品岗转型难度更高，建议先走 TP 路线积累背书。

confidence: medium
evidence_used: ["career-path-patterns: backend-to-pm", "role-taxonomy: product-manager"]
```

**置信度**：medium（路径规律有数据支撑，但个体差异影响实际结果）

**为什么可信**：区分了高把握判断（可迁移能力）和个体差异部分（时间线），没有给出"一定行"或"一定不行"的过强结论。

## 示例 10：主理人总入口 — 我想投字节，这是 JD 和简历

**用户输入**：
> 我想投字节飞书产品经理，这是 JD（附件 1）和我的简历（附件 2）。

**调用的 skill**：`career-principal` 编排 4 个下游 skill

编排顺序：
1. `jd-analyzer` — 解析 JD，提取岗位核心要求和风险信号
2. `profile-builder` — 从简历提取结构化能力画像
3. `match-diagnosis` — 输出匹配分数和差距分析
4. `resume-tailor` — 针对差距生成简历改写建议

**聚合输出**（缩略）：
```
career-principal 综合分析报告

岗位：字节跳动 飞书 产品经理
候选人：[用户简历概要]

--- JD 解析 ---
核心要求：产品规划、数据驱动、跨团队协作；to-B SaaS 经验优先
风险信号：无明确 Band 范围

--- 匹配诊断 ---
综合分：68 / 100
主要差距：to-B 产品经验（简历以 to-C 经历为主），数据分析工具使用经验未体现

--- 简历改写建议 ---
第 2 段经历建议：将"负责用户增长"改写为"通过 A/B 测试和漏斗分析推动核心指标提升 X%"
fabrication_check: PASS（建议改写内容均基于简历原文）

--- 下一步行动 ---
1. 按改写建议更新简历
2. 面试前重点准备：to-B 场景设计题、飞书产品使用体验表达

overall_confidence: medium
evidence_chain: ["JD 原文", "用户简历", "knowledge-graph: 字节跳动 Tier 1", "role-taxonomy: product-manager"]
```

**置信度**：medium（字节有 Tier 1 知识图谱记录，JD 解析完整；匹配分基于用户提供信息，差距判断透明可查）

**为什么可信**：career-principal 暴露了完整的 evidence_chain，用户可以逐项核查每个结论的依据来源。所有改写建议都通过 `fabrication_check` 验证，确保无虚构内容。
