# 运维/SRE（运维/SRE · 校招(压力版 · 高标准)）

> 校招职业标尺 · 难度档：`pressure` · 预设ID：`devops-sre-campus-anthropic`

## 五维评分标尺（权重之和 = 100；score 封顶各维满分，total_score = 各维之和）

### 1. 生产故障定位与根因闭环（满分 26）
- **好的样子**：头部大厂 SRE 卡分线:有真实(哪怕实习/Homelab 仿真)生产级故障的全闭环——按 SEV1-4 评估影响面、定位到内核/网络/中间件具体某一层、给出可复现的根因(不是只贴现象),并交付过 blameless postmortem(无指责复盘:时间线重建 + 5 Whys 逐层追问到根因 + 带 owner 的整改项)。能给出 MTTD/MTTR 的真实数字与改善前后对比,而非"优化了稳定性"。最强的应届能讲清"用 strace/tcpdump/perf 在哪一层抓到证据、排除了哪些假设"。
- **应届证据**：带时间线与 5 Whys 的故障复盘文档(自建或实习项目);MTTD/MTTR 量化改善记录;CKA 上机证;实习中担任 IC/responder 角色的真实记录;CNCF 社区提过涉及稳定性的 Issue/PR;技术博客里一篇"从现象到根因"的完整排障复盘。
- **常见缺失 / 反模式**：只贴现象不挖根因,把"重启好了"当解决【Anthropic 反模式·symptom-not-root-cause:停在症状层,没做 5 Whys 追到真正的内核/配置/容量根因,同类故障必然复发】;复盘变追责或全是"以后多注意"的空话【Anthropic 反模式·blameless 缺失:postmortem 没有时间线、没有带 owner 的可执行整改项,等于没复盘】;故障描述靠脑补、把"猜测"当结论【Anthropic 反模式·speculation-over-facts:incident 更新要"只讲已知事实、不臆测",简历却通篇"可能是""应该是"】。

### 2. 高可用架构与容量设计取舍（满分 24）
- **好的样子**：头部门槛是"会做容量与可用性的工程取舍",不是会装环境:能做负载估算(QPS/连接数/带宽/存储增长),讲清水平扩展 vs 垂直扩展为何这么选、failover/冗余/多活如何设计、SLI/SLO 怎么定与错误预算如何用。关键是把每个决策的 trade-off 讲明白(成本/复杂度/团队熟悉度/上线时间),并说得出"系统长大后哪一处要重新设计"。限流/熔断/降级是带阈值依据的方案而非名词。
- **应届证据**：带容量估算与 SLI/SLO 设计的项目文档;一份对照 ADR 风格(列了选项 A/B + 取舍 + 后果)的架构决策记录;实习中参与过容量评估/扩容/多活演练;限流熔断降级方案里写明阈值是怎么算出来的;压测报告(目标 QPS、瓶颈定位、调优前后)。
- **常见缺失 / 反模式**：只会列组件名,讲不出为什么这么选、放弃了什么【Anthropic 反模式·trade-off 缺失:架构决策不写"考虑过的选项与取舍",直接给结论,面试官一问"为什么不用 X"就崩】;容量靠拍脑袋没有负载估算【Anthropic 反模式·no load estimation:不做 QPS/容量测算就声称"支撑高并发",数字经不起追问】;只考虑当下、不留演进余地【Anthropic 反模式·ignore-future-scale:讲不出"系统长大后哪里要重做",设计无前瞻】。

### 3. 可观测性体系工程化（满分 18）
- **好的样子**：头部要求把 Metrics/Logs/Traces 三支柱做成可治理的体系:搭过 Prometheus+Grafana+Alertmanager 全链路并说得清指标选型逻辑(为何监这几个、SLI 怎么映射到告警),做过告警降噪/分级/抑制并给出误报率/告警量下降的数字,链路追踪(Jaeger/SkyWalking)能定位到跨服务的具体瓶颈。考察的是"告警能不能驱动正确的故障响应",而非大盘好不好看。
- **应届证据**：可复现的监控配置仓库(GitHub);告警治理记录(误报率/MTTD 改善数字);把某次故障的根因映射回"当时缺了哪个指标/告警"的反思;实习中参与 SLO 看板或告警分级建设;Loki/ELK 日志聚合 + Trace 链路打通的端到端 demo。
- **常见缺失 / 反模式**：监控只到"装好能出图",没有指标选型与告警设计思路【Anthropic 反模式·vanity dashboard:大盘截图很多,讲不出每个指标对应哪条 SLI、为何报警】;告警只增不治,噪声淹没真问题【反模式·告警风暴:不做降噪分级,真故障被海量误报埋掉,可观测性形同虚设】;三支柱割裂,出事时 Metrics/Logs/Traces 串不起来定位不了根因。

### 4. 自动化工程与基础设施债治理（满分 18）
- **好的样子**：头部把 SRE 与"操作员"区分开的核心:用 Shell/Python(Go 加分)写过真正上线的运维工具/平台(巡检、发布流水线、CMDB、作业调度)并有效果数字,用 Terraform/Ansible 做过 IaC 消除手工部署。更高一档是能识别并治理基础设施债(手工部署/无监控/无 IaC 属高风险 infra debt),会用"影响×风险×(修复难度)"这类优先级框架排治理顺序,而不是哪个顺手修哪个。
- **应届证据**：GitHub 上有 commit 历史的运维工具/平台仓库(把 N 小时手工巡检降到分钟级);Terraform/Ansible 的 IaC 实操;GitLab CI/GitHub Actions + ArgoCD 流水线;一份"现状有哪些基础设施债、按什么优先级治理"的清单或文档;实习中参与平台研发或自动化改造的量化结果。
- **常见缺失 / 反模式**：只写"会写 Python 脚本"无仓库无上线效果【Anthropic 反模式·manual-toil-not-automated:重复手工操作不沉淀成代码/IaC,典型操作员而非工程师】;识别不出也不治理基础设施债,手工部署/无监控长期裸奔【Anthropic 反模式·infra-debt-ignored:把"能跑就行"当达标,不评估 manual deploy/无 IaC 的高风险】;盲目重构没有优先级依据,捡了芝麻丢了西瓜。

### 5. Linux 底层与网络原理深度（满分 14）
- **好的样子**：头部一面会从一个命令一路追到内核:不仅会敲命令,更要讲清进程/线程与内存管理、IO 多路复用(epoll)、TCP 握手挥手为何如此、拥塞控制、DNS 全链路解析、OOM 触发与定位。能说出"在什么故障场景下用 top/strace/tcpdump/perf 看哪个内核指标、据此排除了哪条假设"——把底层原理直接绑定到故障定位的证据链上。
- **应届证据**：操作系统/计算机网络课程能在连环追问下讲清机理;Homelab 的内核级排障笔记;RHCE 证;自建 Nginx/MySQL/Redis 的调参与踩坑记录(写得出为什么这么调);一篇把 TCP/epoll/OOM 原理讲到位的原创博客。
- **常见缺失 / 反模式**：技能栏堆 Linux/网络词,问 TCP 握手为何不是两次、epoll 比 select 强在哪就卡壳【Anthropic 反模式·command-recitation:背得出命令,讲不出它读的是哪个内核指标、为什么用它】;只会现象级描述,讲不清"用 strace 抓到的系统调用说明了什么"【反模式·浮于表面:原理与排障两张皮,底层知识不能转化为定位能力】。

## 打分解释规则（每维 why 必须落到简历事实；命中反模式直接点名；严禁泄漏"满分的X%/扣X分"等内部计算）
每个维度必须给出 why,且分数与 why 严格一致:① 指出简历中具体命中/缺失的事实(是否有带时间线+5 Whys 的故障复盘、MTTD/MTTR 数字、容量估算与架构取舍、ADR 式选项对比、告警治理量化、IaC 与自动化仓库及上线效果、基础设施债识别、内核/网络原理能否绑定到排障证据链、CKA/RHCE、CNCF 参与),写进 evidenceFound/gap;② 说明在校招运维/SRE 压力档语境下为何重要(头部 SRE 本质是在应届里找"能在生产故障中独立追到根因、能做容量与可用性工程取舍、能写代码消灭重复劳动"的初级系统工程师,标尺远严于普通运维);③ 命中反模式直接点名(symptom-not-root-cause / blameless 缺失 / speculation-over-facts / trade-off 缺失 / no load estimation / vanity dashboard / manual-toil-not-automated / infra-debt-ignored / command-recitation 等),说清踩中的具体证据,不得空泛。严禁泄漏任何"满分 X%/扣 X 分"等内部评分口径,只描述事实与反模式。满纸"熟悉/了解/优化了稳定性"却零根因闭环、零容量取舍、零量化的简历不得给中高分。

## 改写指引（禁编造铁律）
禁编造铁律:只对简历"已有"的故障/架构/自动化/排障句做精准化改写,严禁替候选人添加原句没有体现的能力、技术名词或数据规模。改写侧重:把模糊运维表述讲精准——讲清用了什么技术、定位到哪一层、解决什么问题、量级多大,用 SRE 精准动词(定位/复盘/根因分析/容量评估/降噪/调优/沉淀自动化)与可量化指标(MTTD/MTTR/SLO/告警量/巡检耗时/QPS)增强可信度;把"参与了监控建设"按原文已写明的 Prometheus/Grafana 范围讲精准,不拔高。缺数字处用 [具体数字] 占位并在 reason 注明"建议补充真实工具读数/复盘数据"。严禁把"协助/参与"夸大为"独立/主导";简历没写过 5 Whys 复盘、没写过容量估算、没写过 Go、没写过 IaC,就一律走 gap_advice(如"建议补充:若有真实故障复盘,按 SEV 评级→时间线→5 Whys 根因→带 owner 的整改项补一条"),绝不编造进改写句。original 必须是简历原文一字不差。

## 本土惯例与硬规则
中国校招运维/SRE 压力档惯例核查:① 学历硬规则——头部(字节/阿里/腾讯)SRE 实筛多为本科及以上,非 985/211 需显著补偿项(CNCF 开源贡献/云原生竞赛奖/大厂实习);计算机/网络/软件为核心专业,非科班须强证自学路径与生产级实操。② 证书优先级——CKA(上机实操,含金量最高)> RHCE > 华为 HCIE-Cloud/openEuler(政企央企权重高)> 阿里云 ACP > AWS/GCP(外企有效);一个 CKA 上机证胜过三个笔试认证。③ 格式——应届一页为主、最多两页;技能栏严禁词云堆砌,每个技术点必须有项目/实习/复盘佐证;项目用"背景→角色→技术取舍→量化结果"结构,故障经历用"SEV 评级→定位证据→根因→整改"结构。④ 反信号(压力档加严)——只写部署不写排查与根因;复盘无时间线/无 owner;架构只堆组件不讲取舍;把跑通的玩具包装成"亿级高可用平台"(一问容量估算即穿帮);培训班速成痕迹(知名机构证明 + "系统学习了 K8s")在头部直接降权;过多产品/运营类实习而零生产级技术实操。
